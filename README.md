# Semantic SQL Agent

Ask plain-English questions across several business files and get an answer, a table, a chart and the exact SQL behind it, without letting a language model write the SQL.

A governed **semantic layer** holds the business definitions (what "turnover" means, which totals must never be summed, which files may be joined and how). A deterministic **resolver** maps each question onto those definitions, a **LangGraph** agent turns it into a validated plan, and **code** renders and checks the SQL. A model is optional: it can refine the plan and rewrite the answer, but it can never make a query unsafe, and every number it writes is checked against the result.

The repository also contains the production path around it: Docker images, Kubernetes manifests deployed to a real cluster in CI, an Airflow refresh pipeline with an evaluation gate, MLflow tracking and Prometheus/Grafana monitoring.

> All data here is **synthetic** (invented brands and companies) and is generated by `scripts/generate_data.py`. It deliberately reproduces the traps that break naive text-to-SQL on real commercial data.

---

## Why not just let the model write SQL?

Because on real data it fails in ways that look correct. The demo data reproduces each one, and the system handles each one:

| Trap in the data | What naive text-to-SQL does | What happens here |
|---|---|---|
| `cat_sales` is a category total copied onto every brand row | `SUM(cat_sales)` inflates it ~10x | Detected statistically at build time; de-duplicated with `MAX` per key before summing; the validator rejects a plain `SUM` |
| `LEVEL` mixes brand, manufacturer and category rows | Totals count the same sales three times | Detected as a hierarchy column; `LEVEL = 'brand'` applied by default |
| "Total Acquisition Turnover" is zero on 99% of rows | "revenue" sometimes resolves to it | Generic vocabulary is kept on the plainest column only |
| Brand codes differ across files (`HC` vs `Home Care`) | Joins silently drop everything | Join alignment is measured; a 0% join is disabled and the question is refused with the reason |
| `Glint` in one file is `Glint Dishwash` in another | Rows drop out of cross-file answers | An entity crosswalk maps them, and the answer says it did |
| Three time formats; files end in different months | "Last 3 months" compares different months | Each file gets its own resolved window; differences are reported |
| "excluding Lumen" | Filters *to* Lumen, or drops NULL rows | Negation is scoped and written NULL-safe |
| A brand launched last year | Tops a growth ranking at +100,000,000% | Small bases are flagged and ranked after comparable rows |
| "2x2 matrix" when `Matrix` is also a brand | Filters on the brand | Read as the shape of the answer, and the assumption is stated |

## Architecture

```mermaid
flowchart LR
    Q[Question] --> U[understand<br/>resolver + parser<br/>deterministic]
    U -->|no measure| C[clarify]
    U --> P[plan<br/>optional model refine,<br/>validated or discarded]
    P --> CO[compose<br/>SQL built in code<br/>+ validator + cache]
    CO --> E[execute<br/>Polars, read-only]
    E -->|empty| D[diagnose]
    E --> S[synthesize<br/>answer + citation check<br/>+ audit + memory]
    D --> S
    subgraph Semantic layer, built offline
      B[bootstrap from data] --> O[human overrides<br/>config/semantic_overrides.yaml]
      O --> A[(versioned artifacts)]
    end
    A -.-> U
```

**Build time** (`python -m sqlagent.preprocess`): profile the files, infer roles, entities, joins, repeated bases and hierarchy columns, merge the human-approved overrides, build the value index and the time index, run data-quality gates, and write a versioned artifact set.

**Question time** (`LangGraph`): `understand -> plan -> compose -> execute -> synthesize`, with branches for clarification, refusal, cache hits and empty results. Conversation memory is a LangGraph checkpointer, so "now for Glint" re-uses the previous measure, grouping and period.

More detail: [docs/architecture.md](docs/architecture.md).

## Quick start

```bash
make setup && . .venv/bin/activate
make build        # generate synthetic data, build and promote artifacts
make test         # 24 unit tests
make eval         # golden-set evaluation, logged to MLflow
make api          # http://localhost:8000/docs
make ui           # http://localhost:8501
```

Or with Docker: `docker compose up --build` (API on :8000, chat UI on :8501). Add `--profile monitoring` for Prometheus (:9090) and Grafana (:3000), and `--profile mlops` for an MLflow server (:5000) plus an evaluation job.

Try: *Top 5 brands by revenue in 2025*, then *Now for 2024*. *Which brands grew fastest in 2025 vs 2024*. *Market share trend for Spark*. *Marketing intensity by brand in 2025*. *2x2 matrix of brands by turnover and gross margin in 2025*.

### Using a model (optional, free options exist)

Set `LLM_PROVIDER`, `LLM_BASE_URL`, `LLM_API_KEY`, `PLANNER_MODEL` and `WRITER_MODEL` (see `.env.example`). Any OpenAI-compatible endpoint works, including Gemini's OpenAI-compatible API, Groq and a local Ollama server. Free tiers and model names change, so check each provider's current terms.

## Evaluation

`eval/golden.yaml` holds 30 questions, including a follow-up conversation and two that must be refused. Expected answers are computed **independently** in `eval/reference.py` with plain Polars written against the raw files (not through the semantic layer), and scored on **execution match**: the labels and numbers in the answer must equal the reference within 1e-6. SQL text is never compared.

Current result in deterministic mode (no model): **30 / 30**, mean latency ~15 ms per question. The same set also passes on other random draws of the data (seeds 8, 11, 23, 42), and CI re-checks two of them, so the logic is not tuned to one dataset. Each run is logged to MLflow with its parameters, metrics and report, and CI fails on any regression against `eval/baseline.json`.

**Read this number honestly.** The golden set was written alongside the system, so it is a regression suite that proves fixed bugs stay fixed. It is not an estimate of accuracy on questions nobody has seen. The next step for a real accuracy figure is a set written by business users who did not build the system.

## Deployment and MLOps

| Piece | Where | Status |
|---|---|---|
| Docker | `docker/Dockerfile`: one multi-stage file, targets `api`, `ui`, `tools`, `demo`; non-root; healthcheck | Built and smoke-tested in CI on every push |
| Kubernetes | `deploy/k8s`: kustomize base (Job, Deployment, Services, PVC, ConfigMap, NetworkPolicy) + `kind` and `production` overlays | Deployed to an ephemeral **kind** cluster in CI and smoke-tested through the Service. Not running in a managed cloud cluster |
| Airflow | `airflow/dags/semantic_refresh.py`: detect, validate, build, evaluate, promote, verify; local or KubernetesPodOperator mode | Local mode runs end to end in CI (`airflow dags test`): new data is validated, built, evaluated, promoted, and the live API is checked to have switched versions. Kubernetes mode is parse-tested only |
| MLflow | Evaluation runs (params, metrics, report) via `eval/run_eval.py`; server in Compose | Working locally and in CI (`mlflow.db` uploaded as a CI artifact) |
| CI/CD | `.github/workflows/ci.yml`: lint, tests, eval gate, DAG check, Docker, kind deploy, push to GHCR | Runs on every push and pull request |
| Monitoring | `/metrics` (Prometheus), Grafana dashboard provisioned in Compose, JSON logs to stdout | Working in Compose |

Design notes worth knowing:

- **Preprocess is a Job, not an init container**: building artifacts is slow and should happen when data changes, not on every pod restart. The API waits for promoted artifacts with a small init container.
- **One API replica, `Recreate` strategy**: every replica loads all files into memory and the state volume is ReadWriteOnce; a rolling update onto another node would hang on a Multi-Attach error. Scale vertically first. Measured peak RSS on the demo data is ~170 MB; the limit is 512Mi.
- **Promotion is a pointer swap** (`artifacts/CURRENT`), and the API hot-reloads when it changes. Rollback is promoting the previous version.
- **A build is only promoted if it passes the golden set.** The Airflow DAG evaluates the new build (`ARTIFACT_VERSION=<new>`) before switching traffic, then verifies the API actually serves it.
- **Schema drift is caught at ingest**: a column that disappears, a table that empties or a row count that jumps blocks the build.

Operations guide: [docs/runbook.md](docs/runbook.md). Free hosting of the demo: [docs/hosting.md](docs/hosting.md).

## API

| Endpoint | Purpose |
|---|---|
| `POST /ask` | `{"question": "...", "thread_id": "optional"}` -> answer, rows, chart spec, SQL, plan, confidence, assumptions, notes |
| `POST /ask/stream` | Same, as server-sent events: one event per graph stage, then the answer |
| `GET /ready`, `GET /health` | Readiness (artifacts loaded) and liveness |
| `GET /version` | Artifact version, data version, semantic model summary |
| `GET /schema`, `GET /semantic` | Columns with roles; the full semantic model |
| `GET /decisions` | Recent audit records (one per question, written even on failure) |
| `POST /admin/reload` | Load a newly promoted artifact version |
| `GET /metrics` | Prometheus metrics |

```
  semantic/        model, bootstrap, value index, time layer, resolver
  parser.py        question shape, plan contract (Pydantic), confidence score

```

## Limitations

- Synthetic data only. The patterns come from real commercial data, but the values are generated.
- Query execution is in-process Polars. A warehouse would need a new executor and dialect checks.
- The model-assisted path is optional and is not part of the CI evaluation, which runs fully deterministic.
- Questions outside the supported shapes (ranking, breakdown, trend, pareto, growth, 2x2, cross-file compare, totals) are refused rather than guessed.
- Not deployed to a managed cloud cluster; Kubernetes is exercised on kind in CI.
